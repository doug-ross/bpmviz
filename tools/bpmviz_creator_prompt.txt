# Task: Generate BPMN Explorer Config Files from a Process Diagram

You will be given a **business process diagram** (BPMN, flowchart, swimlane diagram, or similar). Your job is to produce **three JavaScript files** — `branding.js`, `process.js`, and `samples.js` — that conform exactly to the contracts below. These files plug into an existing visualizer engine; you must not invent new fields or change the schemas.

---

## Step 1: Analyze the PDF

Before writing any code, extract and list the following from the diagram. Show your work in a short analysis block at the top of your response.

### 1a. Process identity
- **Process name** (e.g., "Mortgage Underwriting", "Insurance Claim Triage")
- **Domain / industry** (e.g., banking, healthcare, manufacturing)
- **Likely organization type** if visible (department names, system names, regulatory references)
- **Trigger event** — what starts the process (single noun phrase like "Application Received")
- **End state(s)** — what completes it

### 1b. Swimlanes (actors / systems / roles)
List every horizontal lane in top-to-bottom order. For each lane capture:
- Short ID (lowercase, no spaces, max 10 chars)
- Display name (Title Case, max ~24 chars)
- Suggested accent color (see palette below)

If the diagram has no explicit lanes, **infer 4–8 lanes** by grouping tasks by likely actor/system (e.g., "Customer", "Intake System", "Underwriter", "Risk Committee", "Core Banking"). Document your inference.

### 1c. Nodes
List every shape in the diagram. For each, capture:
- **ID** (camelCase, max ~16 chars, unique)
- **Type**, one of:
  - `start` — circle, thin border, entry point
  - `end` — circle, thick border, normal exit
  - `endTerminate` — circle with filled inner circle (process killed)
  - `eventMessage` — circle with envelope (wait state, external trigger)
  - `gatewayX` — diamond with X (exclusive — pick one branch)
  - `gatewayP` — diamond with + (parallel — all branches)
  - `taskUser` — rectangle, human task
  - `taskService` — rectangle, automated/system task
  - `taskScript` — rectangle, business-rules/script task
- **Label** (use `\n` for line breaks; max 2 lines, ~14 chars per line)
- **Lane ID** it belongs to
- **Column index** (0 = leftmost; increment left-to-right following flow order)
- **Description** (1–3 sentences explaining what happens; infer plausibly if not stated)
- For tasks only:
  - **`avg`** (typical duration in minutes) — infer from task nature
  - **`sla`** (target deadline in minutes) — typically 1.5×–4× the avg

### 1d. Flows (sequence flows / arrows)
List every arrow as a `[from, to, optionalLabel]` triple. Labels are only required on flows exiting an exclusive gateway (e.g., "Yes", "No", "Approved", "Rejected").

### 1e. Sample scenarios
The visualizer needs **3–5 in-flight examples** that exercise different paths through the gateways. Invent realistic-but-plausible scenarios that cover:
1. A clean happy-path completion (`status: 'completed'`)
2. An in-progress mid-flow item (`status: 'in-progress'`)
3. A newly-started item (`status: 'new'`)
4. A stuck/escalated item past SLA (`status: 'stuck'`)
5. (If a dispute/rework branch exists) a disputed item (`status: 'disputed'`)

For each sample, pick a different gateway-branch combination.

### Hard rules for `process.js`

1. **Column assignment:** Walk the diagram left-to-right following sequence flows. Each node's `col` is its depth from `start` (which is `col:0`). If two nodes are at the same flow-depth, give them the same `col`. **Maximum reasonable col is ~18**; if your process is wider, consider whether some serial subtasks should be merged.
2. **Lane assignment:** Every node must reference a `lane` ID that exists in `LANES`.
3. **No orphan nodes:** Every non-start node must have at least one incoming flow; every non-end node must have at least one outgoing flow.
4. **Gateway flow labels:** Every flow exiting a `gatewayX` must have a label. Flows exiting `gatewayP` should have no label.
5. **SLA values are minutes** (not hours or days). 1 hour = 60. 1 day = 1440. 1 week = 10080.
6. **Labels with `\n`:** Use exactly one `\n` to wrap into 2 lines. Never use 3 lines.
7. **`avg` must be less than `sla`** for non-wait-state tasks.

## Step 4: Write `samples.js`

Use this **exact** structure. Keep the `buildPath` helper exactly as-is.

```js
/* ============================================================
   SAMPLES — exercising different paths through <Process Name>
   ============================================================ */

function buildPath(steps){
  let t = 0; const out = [];
  function walk(arr){
    for (const s of arr) {
      if (Array.isArray(s[0])) {
        const startT = t; let maxEnd = startT;
        for (const branch of s) {
          let bt = startT;
          for (const [nid, dur] of branch) { out.push({nodeId:nid, t:bt, dur}); bt += dur; }
          if (bt > maxEnd) maxEnd = bt;
        }
        t = maxEnd;
      } else {
        const [nid, dur] = s;
        out.push({nodeId:nid, t, dur});
        t += dur;
      }
    }
  }
  walk(steps);
  return out;
}

const SUBMISSIONS = [
  {
    id:'<shortid>',
    name:'<Specific item name> · <one-line status>',
    client:'<Counterparty / customer name>',
    engagement:'<Type of work / product>',
    fees:'<$ amount or volume metric>',                // optional but keep field
    partner:'<Owning person>',                          // optional but keep field
    office:'<Location>',                                // optional but keep field
    status:'in-progress',                               // see allowed values below
    summary:'<2–3 sentence narrative of current state>',
    path: buildPath([
      // [nodeId, durationMinutes] for each step the item actually traversed
      // For gateways, include them with dur:0
      // Only include nodes the item actually visited (not pending future ones)
      // Wait, no — include ALL nodes the item WILL visit through end; the
      // simulation animates forward through them. pauseAt determines where
      // 'now' freezes.
      ['start',0],
      ['<nextNode>', <minutes>],
      // ... continue to an end node
    ]),
    pauseAt: <minutes>      // simulation time at which this sample is "now"
  },
  // ... 3–5 total
];
```

### Hard rules for `samples.js`

1. **Allowed `status` values:** `'in-progress' | 'new' | 'stuck' | 'completed' | 'disputed'`
2. **Every `path` must end at an `end` or `endTerminate` node** — even for in-progress items. The path describes the *projected full route*; `pauseAt` controls where playback is currently frozen.
3. **Gateways must appear in the path with `dur:0`** at the moment the decision was made.
4. **Through an exclusive gateway, only include the branch actually taken** (do not include both branches).
5. **`pauseAt` placement by status:**
   - `'new'` → very early (within first 1–2 tasks, e.g., 5–60 minutes in)
   - `'in-progress'` → mid-flow (30%–60% of total path duration)
   - `'stuck'` → at or past the SLA boundary of a specific task
   - `'disputed'` → inside the dispute/rework branch
   - `'completed'` → set to `999999` (past total) so the whole path renders done
6. **Realistic durations:** Use `avg` and `sla` from `process.js` as your baseline. For stuck items, exceed `sla`. For clean items, run near `avg`. Add ±20% variance.
7. **Sample variety:** Across all 3–5 samples, ensure every gateway branch in the diagram is exercised by at least one sample.
